DualWindow-MSS

A causal vocal separator that answers within 5.8 or 2.9 milliseconds, and a window design that wins back much of the quality that short windows lose.

Qing (Arya) Zhonglisten ↓code ↗

01 / Problem

The latency budget

Live sound, in-ear monitoring and hearing devices need the voice separated from the band within a few milliseconds. Offline separators such as HTDemucs read seconds of future audio. A causal separator cannot, and in a short-time Fourier transform (STFT), the synthesis window determines the algorithmic wait.

How much quality does a causal separator lose at 5.8 or 2.9 ms, and can the window design win part of it back without adding latency? Three hypotheses were written down before the experiments:

H1

A long analysis window with a short synthesis window recovers quality at the short window’s latency.

+0.76 dB per song at 5.8 ms and +0.73 dB at 2.9 ms; 45 of 50 songs improve at each latency.

H2

Extending the analysis window costs compute, not latency.

Measured look-ahead 247 ≤ 255 and 123 ≤ 127 samples, unchanged by the long window; about 2× the CPU time of the short-window baseline.

H3

The gain does not depend on a large model.

+0.54 to +0.76 dB from 0.17 M to 0.94 M parameters.

A window is a wait

The model may only look through a window.

Read the time axis from left to right: older samples on the left, the newest sample at now on the right. An STFT separator cuts the stream into windows and can process one only once all of its samples have arrived.

So the window length is a wait: with 1024 samples at 44.1 kHz, the worst-case algorithmic wait is about 23.2 ms. Too long for a singer’s in-ear monitor.

1024 samples · 43 Hz per bin

What the model sees is a spectrum.

Each window is turned into a spectrum, and the separator decides, bin by bin, how much of the energy is voice. A long window gives fine bins: 43 Hz apart, so every harmonic of the sung note (white ticks) stands apart from the accompaniment (gray ticks).

256 samples · 172 Hz per bin

Cut the wait, lose the detail.

A 256-sample window answers within 5.8 ms, but its bins are 172 Hz apart. Neighboring partials of the voice and the accompaniment land in the same bin and start to merge.

128 samples · 345 Hz per bin

At 2.9 ms, a blur.

With 128 samples the bins are 345 Hz apart. Only five bin centers lie between 0 and 1.6 kHz. Voice and accompaniment are harder to distinguish, so the mask has less detail to work with.

02 / Idea

Look back long, answer short.

A dual window splits the two jobs (Mauler & Martin, 2007). The analysis window, 2048 samples, reaches far into the past and gives the model a sharp spectrum again. The synthesis window, 128 samples, decides when the output may leave.

Only the synthesis window sets the wait: still 2.9 ms.

Nothing is lost on the way out.

The synthesis window is shaped so that analysis × synthesis is a plain 128-sample Hann window. Overlapping those every 64 samples adds up to exactly one, so a signal that passes through untouched comes out exactly as it went in.

The analysis window adds no delay.

Looking further into the past costs nothing in time, because the past has already arrived. The trained models confirm it: the output reacts to an input change after at most 123 samples (bound 127), the same as the short window. How this was measured: chapter 06.

03 / How it works

One small network, five windows

Every configuration A–E uses the same pipeline and network architecture, trained separately for its window pair; only the windows and the hop change. The network is deliberately small, 0.94 M parameters, because it has to finish every block before the next one arrives.

A–E are model names. Windows are analysis / synthesis samples; hop = synthesis / 2.

Fig. 3 · the pipeline

Shown: D at 2.9 ms, with one 64-sample block per hop. Stages light up as the text describes them. The final compute comparison uses C and B, both at 5.8 ms. Source ↗

Blocks in, blocks out.

Audio arrives in blocks of 64 samples (one hop, 1.45 ms at 2.9 ms latency). Each new block is appended to a buffer of the recent past, and the chain runs once.

The transform decides the latency.

The analysis window reads the last 2048 samples of the buffer and produces 1025 frequency bins. The synthesis window, used at the far end, covers only the last 128 samples: that is the only part of the output that has to wait.

A small, causal network.

A convolutional encoder runs along frequency with weights shared across bins, pools to 64 bands, and one causal GRU layer carries context forward in time, never backward. Weights are shared across frequency bins within each model; each window configuration is trained separately.

A mask, not a new signal.

The head outputs one gain between 0 and 1 per bin. The vocal estimate is the mixture spectrum multiplied by this mask, so the system attenuates mixture bins rather than generating a new spectrum; it keeps the mixture phase.

Back to audio, one hop later.

The masked spectrum goes through the inverse transform with the short synthesis window, overlap-added with the previous block. The streaming implementation shifts the reconstructed signal by one hop. Waiting for an input block to fill adds up to one more hop minus one sample: 127 samples in the worst case.

Where the compute goes.

The encoder and the mask head run on every bin, so the dual window pays for its 1025 bins where the short window has 129: 5.84 against 1.55 million multiply-adds per frame. These per-bin layers dominate the dual-window cost. Widening the GRU also adds compute, which is tested separately below.

Training and evaluation

The same recipe for every window

Using the same data, objective and training recipe makes the window comparison controlled. Model size, compute and learning-rate checks below probe other explanations.

Data

MUSDB18-HQ, mono at 44.1 kHz: 86 songs for training, 14 for validation and model selection, the 50 test songs only for the numbers reported here.

Loss

Computed on the synthesized waveform (L1 plus a multi-resolution STFT term), so every window pair is judged on the audio it outputs, not on its own spectrum.

Training

200 k updates with random stem gains, cross-song remixing and 20% vocal-dominant mixtures; the checkpoint with the best validation SI-SDR is kept; two seeds per configuration.

Metric

Vocal SI-SDR measures how closely the separated vocal matches the clean vocal after allowing an overall gain change; higher is better. It is scored on each full test song, with seeds averaged. HTDemucs, an offline reference that sees seconds ahead, reaches 8.49 dB on the same mono input.

Comparisons

Always paired per song: the median of the 50 per-song differences, with a bootstrap 95% confidence interval over songs (10,000 resamples), and the count of songs that improve.

Why medians

A few songs have almost no vocal. On one of them single runs score −13 to −50 dB, which would dominate any mean; medians report what happens on most songs. Means are given alongside.

04 / Why it works

What the window lets a mask recover

Before any training, an oracle experiment asks what each window pair can recover with an ideal ratio mask computed from the true stems. This is a diagnostic reference, not a proven upper bound for every possible separator. That separates what the window allows from what the network manages to learn.

Fig. 4 · ideal masks

Ideal ratio masks: uSDR on 30-second excerpts of the 14 validation songs. The gain comparison uses full-test-song SI-SDR. These are different evaluation settings. Octave losses: output vocal energy relative to the clean vocal with simulated bleed, 50 test songs. Source ↗

Short windows lose detail even with ideal masks.

With ideal masks, symmetric windows lose about 3 dB between 23.2 and 2.9 ms. This loss appears before a network is trained: the window representation itself matters.

A long analysis window recovers detail.

At 5.8 ms, a 2048-sample analysis window (10.06 dB) beats a symmetric window at twice the latency (9.52 dB at 11.6 ms). Going to 4096 adds nothing, which is why 2048 was chosen, on validation songs only.

The trained models realize about 40% of it.

On the test songs the oracle gain of the dual window over the short window is +1.87 dB, positive on every song. The trained 0.94 M models turn it into +0.76 dB. The remaining gap leaves room to improve the estimator and its training; this experiment does not identify a single cause.

The loss sits in the low voice.

Where does the short window lose? Mostly in the lowest octave of the voice. With simulated bleed, the 256-sample window loses 3.6 dB of vocal energy between 125 and 250 Hz, the dual window 2.6 dB, the long window 2.4 dB.

Resolution is not the whole story: the 128-sample window loses 2.9 dB there, less than 256 samples, and its dual partner 2.2 dB.

05 / Results

Fifty songs, one network

Within each latency the hop and the synthesis window are identical; only the analysis window differs. The main comparison is therefore C against B at 5.8 ms and D against E at 2.9 ms, song by song.

Fig. 5 · per-song gain

One bar per MUSDB18-HQ test song, two training seeds averaged, sorted by gain. Bars above the line are songs the dual window improves; gains below −3 dB are clipped and marked. Source ↗

5.8 ms

45 of 50 songs improve.

Each bar is a test song, raised by how much vocal SI-SDR the dual window gains over the 256-sample window at the same latency. Median gain per song: +0.76 dB (95% CI 0.57 to 0.90).

2.9 ms

The same at half the latency.

Against the 128-sample window: +0.73 dB (0.59 to 0.88), again on 45 of 50 songs. Halving the dual window’s latency from 5.8 to 2.9 ms costs only 0.16 dB per song.

Matched compute

Not just a bigger model.

Widen the short-window network until it costs as many operations per frame, and give it a learning rate chosen on validation data: it closes about a third of the gap. These learning-rate checks were prompted by test results and are exploratory. The dual window still leads by a median 0.50 dB, on 41 of 50 songs.

Failure case

One song goes the other way.

On PR – Happy Daze the voice sits 26 dB below the band. The dual window removes more accompaniment but also more voice, and the song loses 19 dB.

That single song is why the matched-compute mean gain (+0.06 dB, 95% CI −0.82 to +0.59) is far below its median (+0.50 dB). For the original D–E pair the mean is +0.35 dB (−0.57 to +0.91), also inconclusive; most songs improve, but the average gain is uncertain.

Model size

Small models benefit too.

Shrinking the GRU to 0.38 M and 0.17 M parameters keeps the gain at +0.59 and +0.54 dB. The 0.17 M dual-window model even beats the 0.94 M short-window model, by 0.31 dB per song.

06 / Verification

Latency, measured rather than assumed

A claim of 2.9 ms is only as good as the implementation. Two tests check that no code path quietly looks further ahead than the synthesis window allows.

Fig. 6 · the prefix test

Schematic. The measured look-ahead is the largest over 16 positions of the change within a hop, with the trained weights; the bound is the synthesis window minus one. Source ↗

Two inputs that agree, then differ.

Feed the trained model two signals that are identical up to sample n and different afterwards. Compare the outputs aligned to the original signal, before adding the streaming delay. If their first difference is at n − L, output at that position depends on input L samples later.

Where the outputs part is the look-ahead.

The distance from the first changed output to sample n measures look-ahead in the aligned output. Repeat at 16 change positions within a hop and take the largest distance. For the 2.9 ms models it is 123 samples, under the bound of 127; for 5.8 ms, 247 under 255. The 2048-sample analysis window did not add a single sample.

And the frame-by-frame code agrees.

An impulse fed through the streaming code with an identity mask comes out exactly one hop later; with the wait for an input block to fill, the worst case is the synthesis window minus one sample: 127 samples, 2.88 ms. What is not measured: the audio interface’s own buffers.

07 / Cost

Before the next hop arrives

Algorithmic latency is only half of the story: every hop must also be computed before the next one arrives. The full pipeline (STFT, network, inverse STFT) was exported to ONNX Runtime and timed on a single CPU thread.

Fig. 7 · the deadline

one hop = one slot of 1.45 mstime spent computing itfinished after the deadline

Mean time per hop from the benchmark (one Xeon Gold 6150 thread, all models in one job), shown in slow motion. Source ↗

What a hop is.

At 2.9 ms latency a new block of 64 samples arrives every 1.45 ms. Each slot on the track is one such hop. Whatever the model computes for a block has to be finished before the slot ends, or the audio glitches.

Half the budget.

The 2.9 ms dual-window model needs 0.75 ms of its 1.45 ms on average and 0.76 ms at the 99th percentile. 0.01% of hops were late.

The price is compute, not latency.

The 128-sample window alone needs half that time. At the same latency the dual window roughly doubles CPU time: real-time factor 0.515 against 0.262.

Implementation matters.

The same model run in eager PyTorch takes 1.7 ms per hop (real-time factor 1.18) and misses every deadline. A deployed system would run in a dedicated real-time audio thread.

The whole trade-off on one chart.

Lowering latency from 23.2 to 5.8 ms costs 1.05 dB with a short window but only 0.31 dB with the dual window, and 2.9 ms costs another 0.16 dB. What the dual window buys with quality it pays in multiply-adds per frame, about 3.8× to 4.7× its short-window baseline.

08 / A stage situation

The vocal microphone

On stage the vocal microphone does not pick up a clean mix: the band leaks in. In a simulated version, studio stems are mixed with the accompaniment 5 dB below the voice, and the mixture determines a mask. Holding that mask fixed and applying it separately to voice and accompaniment splits the output exactly into the voice kept and the bleed remaining.

Fig. 8 · bleed

Simulated bleed from digitally mixed stems, 30-second excerpts of the 50 test songs; sweeping the mask strength traces each curve. The three paths are fixed synthetic transformations, not real rooms or microphones. Source ↗

Two things to trade.

A separator can always remove more of the band by removing more of everything. The fair comparison is at equal bleed attenuation: how much voice does each model lose while removing the same amount of band?

At 2.9 ms, the dual window keeps more voice.

Sweeping the mask strength traces each model’s curve. At a common 8.9 dB of bleed attenuation the dual window loses 0.67 dB of vocal energy, the short window 0.97 dB; at 5.8 ms, 0.68 against 0.94 dB at a common 9.7 dB attenuation. Each pair uses its own operating point.

And it survives a change of path.

With frozen models, the accompaniment was sent through three fixed paths before mixing: dry, mild filtering plus delay, and a synthetic room. The paired gain of the dual window stays between +0.59 and +0.91 dB on every path, and at equal attenuation it keeps 0.32–0.35 dB more voice.

Limitations

  • Mono vocals on one dataset (MUSDB18-HQ), scored with SI-SDR; no listening test.
  • Small models trained with one recipe, two seeds per configuration; only the GRU width was varied.
  • Gains are medians over songs; at 2.9 ms the mean gain is not significant because of one song with almost no vocal.
  • Timing on one CPU type; end-to-end latency through an audio interface was not measured.
  • Bleed and acoustic paths are simulated; the desk uses ccMixter excerpts, not MUSDB18 audio.
